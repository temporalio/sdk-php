## Rules

### Spot-verify file:line claims before approving plan refinements
**Source**: Nexus proto-native refactor — refined plan claimed `Worker.php:155-160` for Nexus route registration; actual range was `:158-160`. Drift was minor here, but other refs could be more wrong; trusting blindly leaks stale info into implementation pseudocode and downstream docs.
**Rule**: When refining a plan, spot-check 2-3 representative `file:line` refs from the plan body against the actual source via `Read` or `grep`. Plans drift between authoring and refinement (other commits land, line numbers shift). Always verify before approving:
- Class/method names cited in the plan exist
- Line ranges roughly match the actual code
- Cross-SDK alignment claims (Java/Go/TS analogs) point at real symbols
Flag any drift in the refinement report and update the plan in the same pass.

### Close open decisions in the plan, not at implementation time
**Source**: Nexus proto-native refactor — refined plan had two "decide on implementation" notes (assert vs throw, validators move vs drop). Closed both as part of refinement, which prevented stop-and-ask friction during implementation.
**Rule**: Any plan note containing phrases like "decide on implementation", "verify later", "either is defensible", "pick whichever keeps the route simpler", or similar deferred-decision phrasing is a smell. During refinement:
1. Identify the choice and its trade-offs from the plan's own context.
2. Make the call explicit in the plan with a one-line rationale.
3. If you cannot close a decision (e.g. needs user input on architectural preference), surface it in the refinement report as a concrete question — not as "TBD" in the plan.
Open decisions become implementation-time stop-and-ask friction or silent bad defaults. The refinement pass is where they get resolved.

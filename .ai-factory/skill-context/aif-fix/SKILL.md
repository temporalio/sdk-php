## Rules

### Workflow hangs / timeouts in Fiber mode → check `startScope` context save/restore
**Source**: Fiber stabilization — `MutexRunLockedTest::runLockedAndCancel` (60s timeout), `CancelAbandon::childWorkflowInClosingInnerScope` (60s timeout)
**Rule**: When debugging a "Fiber workflow hangs and times out at 60s" symptom (`Temporal\Exception\Client\WorkflowFailedException` with `retryState=3` and event history shows `WORKFLOW_TASK_TIMED_OUT` after the workflow does at least one `Workflow::async(...)` or `Workflow::runLocked(...)` call), first suspect: `Scope::startScope()` context leak. Verify:
```php
public function startScope(...) {
    $fiberMode = $this->scopeContext->isFiberMode();
    $savedContext = $fiberMode ? Facade::getCurrentContext() : null;
    $scope = $this->createScope(...);
    $scope->start(...);
    if ($fiberMode) {
        Facade::setCurrentContext($savedContext);
    }
    return $scope;
}
```
**Root cause**: `Scope::next()::makeCurrent()` inside the child's synchronous start switches `Facade::$ctx` to the CHILD scope. Without restore, the parent Fiber's next `Workflow::await(...)` registers on the wrong scope. Unconditional restore (no `if ($fiberMode)`) breaks Generator workflows that rely on the leak.

### `FiberError: Cannot suspend outside of a fiber` → check `setFiberMode(false)` leak
**Source**: Fiber stabilization — Mutex constructor pre-lock, Query handler clone, mid-flight `Scope::cancel` resets
**Rule**: When debugging `FiberError: Cannot suspend outside of a fiber`, the call path tried to call `Fiber::suspend(...)` while the surrounding PHP frame is NOT inside an active Fiber. Three common Fiber-stabilization causes (in observed-frequency order):
1. **`Scope::cancel()` reset corruption** — A child scope's Fiber is suspended on a Mutex/Deferred; cancel-driven `setFiberMode(false)` flips the flag; when the Mutex resolves later and the bridge resumes the Fiber, the next `FiberHelper::await` checks `isInFiberMode()` and throws. Fix: remove the `setFiberMode(false)` from `Scope::cancel()`. The bridge's `try/finally` is the sole legitimate reset.
2. **Query handler context clone** — `Process::setQueryExecutor` clones the main scope's `ScopeContext` via `withInput()`; `$fiberMode` copies by value. If the main scope is currently in Fiber mode (between suspends), the query handler inherits `true` and any `Fibers\Workflow::*` call inside it throws. Fix: `$context->setFiberMode(false);` right after `setReadonly(true)`.
3. **Mutex constructor pre-lock pattern** (`MutexYieldTest`) — `new Fibers\Mutex()` followed by `$mutex->lock()` from the workflow constructor runs BEFORE `Scope::createFiberHandler` starts the Fiber. `Fibers\Mutex::lock()` returns a no-op resolved promise when `isInFiberMode()` is false. This is intentional and safe for the first lock only — second pre-Fiber `lock()` would silently leak a Deferred. If this pattern appears in a test, verify only one pre-Fiber `lock()` is used.

### Acceptance test passes in isolation, fails in full suite → check shared state / queue routing
**Source**: Fiber stabilization — `Versioning/Fibers/Classic` initially looked like order-dependency
**Rule**: When a test fails ONLY in full suite (not in isolation), the most common cause is NOT genuine ordering pollution — it's a filter-mismatch artifact. PHPUnit's `--filter` is regex with unescaped dots that match all chars; `--filter='Versioning.Classic'` matches both `Versioning\Classic\ClassicTest` and `Versioning\Fibers\Classic\ClassicTest`. Verify isolation with a TIGHTER filter (`--filter='Versioning\\\\Fibers\\\\Classic'`). If still failing in both isolation and suite, the cause is real (e.g. task queue routing per TaskQueueResolver, history fixture mismatch) — not ordering. Don't waste investigation budget on "order-dependent" hypotheses without first re-running isolation with an escaped filter.

**Rule**: When a Fiber acceptance test "passes" but the user/reviewer doubts it actually exercised the Fiber path, the test workflow body probably has `yield` or `: \Generator`. ### Activity `RETRY_STATE_TIMEOUT` in Fibers test → check `executeActivity` name vs `ActivityInterface(prefix:)`
**Source**: Fibers test-replication — 4 tests silently failed for hours with `ActivityFailure: retryState='RETRY_STATE_TIMEOUT'` (`Update/Fibers/SelfTest`, `Update/Fibers/ActivitiesTest`, `Update/Fibers/WorkerRestartTest`, `Signal/Fibers/ActivitiesTest`) — root cause was always the same: workflow called `executeActivity('result')` but `ActivityInterface(prefix: 'Fibers_')` registered the activity as `Fibers_result`. Server timed out the activity because no handler matched the requested name.
**Rule**: When a Fibers acceptance test fails with `Temporal\Exception\Failure\ActivityFailure: retryState='RETRY_STATE_TIMEOUT'` (or `RuntimeException: Activity did not start` polling loop), grep the failing test file:
```
grep -n "Workflow::executeActivity('\|#\[ActivityInterface(prefix" <file>.php
```
If the file has BOTH `#[ActivityInterface(prefix: 'X_')]` and bare-string `Workflow::executeActivity('<name>', ...)`, the wire name registered is `X_<method>` but the workflow asks for `<name>` — server has no handler, times out. Fix: rewrite EVERY bare-string `executeActivity` first argument to start with the same prefix. Activities invoked via `Workflow::newActivityStub(Class::class)->method()` proxy are immune — the SDK resolves names via reflection.

### "Child Workflow execution not found in the history" or fatal `Class not found` → check `Workflow\X` expression refs
**Source**: Fibers test-replication — `CancelAbandonTest`'s 3 sub-tests reported "Child Workflow execution not found in the history. Failed asserting that null is not null." Polling parent history for 10s never found `ChildWorkflowExecutionStarted`. Root cause: `Workflow\ChildWorkflowOptions::new()` and `Workflow\ParentClosePolicy::Abandon` fatally errored with `Class not found` — workflow task fails before issuing the start command — no event ever lands in history.
**Rule**: When a Fibers acceptance test fails with one of these symptoms:
- "Child Workflow execution not found in the history" (parent's history poll loop)
- Fatal `Class not found` in worker log
- Workflow task failures with no commands emitted

Grep the test file for `Workflow\` expression references (not in `use` statements, not preceded by `\`):
```bash
python3 -c "
import re
text = open('<file>.php').read()
for ln, line in enumerate(text.split('\n'), 1):
    if line.lstrip().startswith('use '): continue
    for m in re.finditer(r'(?<!\\\\)\bWorkflow\\\\[A-Z]\w*', line):
        print(f'{ln}: {m.group(0)}')
"
```
Any hit indicates an alias-shadowed class reference. Rewrite each to fully-qualified `\Temporal\Workflow\<Class>`. Most common: `Workflow\ChildWorkflowOptions`, `Workflow\ParentClosePolicy`, `Workflow\CancellationScopeInterface`. Same root cause as the `#[Workflow\X]` attribute case — the fibers facade `use` shadows the attribute namespace.

### Worker boot `Constant X already defined` warning → namespace `\define` in Fiber-mirror
**Source**: Fibers test-replication — `PHP Warning: Constant INPUT_DATA already defined in .../Fibers/ContinueAsSameTest.php on line 15` flooded stderr when both original and replica loaded.
**Rule**: When worker boot or test output shows `PHP Warning: Constant <NAME> already defined in <path>/Fibers/<TestName>.php:<line>`, the Fiber-mirror test re-defines a global constant the original also defines. Edit the Fibers file's bare `\define('NAME', value)` → `\define(__NAMESPACE__ . '\NAME', value)`. References inside the same namespace continue to work via PHP's fallback to namespaced constants. The warning isn't always fatal but masks real failures and indicates test isolation is broken. Common cases: `INPUT_DATA`, `MEMO_KEY`, `MEMO_VALUE`, `WORKFLOW_ID`, `EXPECTED_RESULT`.

### `TIMEOUT_TYPE_START_TO_CLOSE` on Fibers child-workflow test → typed proxy auto-await deadlock
**Source**: Fibers test-replication — `Harness/ChildWorkflow/Fibers/SignalTest::check` and `Harness/Signal/Fibers/ChildWorkflowTest::check` both fail with `WorkflowFailedException ... retryState=3` whose underlying cause is `Temporal\Exception\Failure\TimeoutFailure: TIMEOUT_TYPE_START_TO_CLOSE`. The workflow body uses `Workflow::newChildWorkflowStub(C::class)` + `$wf->run()` + `$wf->signal(...)` + `return $handle` — `FiberProxy::__call` auto-awaits `$wf->run()` until child completes, child blocks on signal that's never sent, deadlock until parent's StartToClose timeout fires.
**Rule**: When a Fibers child-workflow test errors with `WorkflowFailedException ... retryState=3` and the underlying cause is `TimeoutFailure: TIMEOUT_TYPE_START_TO_CLOSE` (not StartToClose of an activity, but of the parent workflow itself), AND the workflow uses a typed child stub (`Workflow::newChildWorkflowStub(C::class)`) followed by separate signal+await pattern, the cause is FiberProxy's mandatory auto-await. Fix: rewrite to untyped stub:
```php
$wf = Workflow::newUntypedChildWorkflowStub('<wire-type>', $options);
$started = $wf->startAsync();
$signaled = $wf->signalAsync('<signal-name>', [<args>]);
$result   = $wf->getResultAsync();
FiberHelper::await($started);
FiberHelper::await($signaled);
return FiberHelper::await($result);
```
There is no opt-out for FiberProxy. The typed proxy is for synchronous one-call execution; multi-step patterns (start, signal, await separately) require untyped stub.
